# SET2-2 リアルタイム対戦：ルーム・状態遷移・結果確定

> ステータス: **ドラフト**
> 対応チケット: [SET2-2](https://linear.app/setsuna-no-puyuri/issue/SET2-2)
> 前提: [SET2-4 の判定方式](./set2-4-sync-fairness.md) は確定済み。本書はその判定を**いつ・どの状態で**実行するかを決める。

## 1. スコープ

- 2人専用ルームの状態遷移
- クライアントとサーバー間の送受信データ仕様
- 重複・順序逆転・古い入力の扱い、結果の一度だけの確定
- 切断・期限超過時の終了とルーム破棄
- 技術候補の比較と採用方針

スコープ外:
- 待機列から2人を選ぶ処理（SET2-3）。本書は「ルームが作られた後」から扱う
- 画面表現（SET2-5）。本書はイベントとデータまで
- 戦績の保存先（SET2-6）。本書は「記録してよいか」のフラグまで

## 2. 識別子

| 名前 | 形式 | 生存期間 | 用途 |
|---|---|---|---|
| `clientId` | サーバー発行の不透明な文字列 | 接続単位 | 送信元の識別。**本人証明には使わない**（SET2-7 の匿名前提） |
| `matchId` | サーバー発行のランダムID | ルーム単位 | 1回のマッチング＝1ルーム＝1マッチ |
| `roundId` | `matchId` 内の連番（MVP は常に 1） | ラウンド単位 | 古いラウンド宛の入力を捨てるために使う |
| `eventId` | クライアント発行の連番 | 接続単位 | 再送・重複の検出 |

MVP は「1マッチ1ラウンド」なので `roundId` は常に 1 だが、**フィールドは最初から持たせる**。
後から足すと、古い入力を捨てる仕組みを後付けすることになり危険。

## 3. 状態遷移

サーバーが持つルームの状態。**クライアントは状態を持つが、正とはみなさない。**
サーバーの `STATE` / `ARMED` / `GO` / `RESULT` を受けて追従するだけ。

```
                    ┌──────────┐
      2人揃う ──────→│ WAITING  │←──────── RESULT 送信後（再戦）
                    └────┬─────┘
                   双方 READY
                         ↓
                    ┌──────────┐
                    │  ARMED   │  ランダム待機 W（1.0〜4.0秒）
                    └────┬─────┘  この間の入力＝フライング
                    W 経過
                         ↓
                    ┌──────────┐
                    │   CUE    │  GO を push、入力期限 T（3.0秒）を開始
                    └────┬─────┘
         双方入力 / 期限超過 / 切断
                         ↓
                    ┌──────────┐
                    │ RESOLVED │  判定し RESULT を push。結果はここで一度だけ確定
                    └────┬─────┘
          再戦 ←─────────┼─────────→ 双方離脱・一定時間無操作
              ↓                              ↓
          WAITING                       ┌──────────┐
                                        │  CLOSED  │  ルーム破棄
                                        └──────────┘
```

### 3.1 遷移表

| 現在 | 契機 | 次 | 副作用 |
|---|---|---|---|
| （なし） | SET2-3 が2人を割り当て | `WAITING` | `matchId` 発行、両者に `MATCHED` |
| `WAITING` | 双方から `READY` | `ARMED` | `roundId` 発行、`ARMED` を push、待機タイマー `W` を開始 |
| `WAITING` | 一方が `LEAVE` / 切断 | `CLOSED` | 相手に `PEER_LEFT`。**無効試合ですらない**（勝負前） |
| `ARMED` | `W` 経過 | `CUE` | `goSentAt` 記録、`GO` を push、期限タイマー `T` を開始 |
| `ARMED` | `TAP` 受信 | `ARMED` | フライングとして記録。状態は変えず、相手を待つ |
| `ARMED` | 切断 | `RESOLVED` | 無効試合（ケース7） |
| `CUE` | 双方の入力が揃う | `RESOLVED` | 判定 |
| `CUE` | `T` 超過 | `RESOLVED` | 無入力を含めて判定（ケース5・6） |
| `CUE` | 切断 | `RESOLVED` | 残った側の不戦勝（ケース8） |
| `RESOLVED` | 判定完了 | `WAITING` | `RESULT` を push、`ready` をリセット |
| `RESOLVED` | 双方離脱 or 無操作タイムアウト | `CLOSED` | ルーム破棄 |

**`ARMED` でのフライングは状態を変えない。** ここで即座に決着させると、
「相手より先にフライングしたほうが早く結果を見られる」だけで、相手の入力機会を奪う。
双方の入力または `W` 経過を待ってから `CUE` に進み、判定時にフライングとして扱う。

> 実装上の注意: 片方がフライングした時点で勝負は決しているが、それを**相手に知らせてはいけない**。
> 知らせると「相手がフライングした」と分かった側が合図を待たずに押せてしまう。
> `RESULT` まで伏せる。

## 4. メッセージ仕様

JSON、1メッセージ1オブジェクト。`type` で分岐する。

### 4.1 クライアント → サーバー

| type | フィールド | 説明 |
|---|---|---|
| `HELLO` | `eventId`, `sessionToken?` | 接続直後。`sessionToken` は SET2-7 が決める |
| `READY` | `eventId`, `matchId` | 準備完了 |
| `TAP` | `eventId`, `matchId`, `roundId`, `flying`, `R?`, 診断値 | 入力。詳細は §4.3 |
| `LEAVE` | `eventId`, `matchId` | 明示的な離脱 |
| `PING` | `eventId`, `seq` | クライアント側の RTT 表示用（判定には使わない） |
| `SPONG` | `seq` | **サーバー発 `SPING` への応答。サーバーが RTT を測るために必須** |

### 4.2 サーバー → クライアント

| type | フィールド | 説明 |
|---|---|---|
| `WELCOME` | `clientId`, `cfg` | 接続確立。`cfg` は `W` 範囲・`T`・`D` 等 |
| `MATCHED` | `matchId`, `peer` | ルーム割り当て。`peer` は表示名のみ（識別子は渡さない） |
| `STATE` | `matchId`, `state`, `members` | 状態同期。再接続時の復帰にも使う |
| `ARMED` | `matchId`, `roundId` | 合図待ち開始。**`W` の値は含めない**（含めると待ち時間が読める） |
| `GO` | `matchId`, `roundId` | 合図。**予告なし・事前配信なし**（SET2-4 §3） |
| `RESULT` | `matchId`, `roundId`, `reason`, `recorded`, `players[]` | 結果。詳細は §4.4 |
| `PEER_LEFT` | `matchId` | 相手が離脱 |
| `PONG` | `seq` | `PING` の応答 |
| `SPING` | `seq` | **サーバーが RTT を測るための ping。クライアントは `SPONG` を返す** |
| `ERROR` | `code`, `message` | 拒否理由 |

### 4.3 `TAP` の中身

SET2-4 の判定と整合性検査に必要な値をすべて載せる。

| フィールド | 型 | 用途 |
|---|---|---|
| `flying` | bool | 合図の表示前に入力したか |
| `R` | number? | 申告する反応時間。`flying` のときは省略 |
| `recvToPaint` | number | `t_paint − t_recv`。計測系の診断 |
| `inputToHandler` | number | `t_handler − t_input`。メインスレッド混雑の診断 |
| `frameInterval` | number | 実効フレーム間隔。リフレッシュレート推定 |
| `visibilityOk` | bool | ラウンド中にバックグラウンド化しなかったか |
| `extraTaps` | number | 連打回数（判定には使わない。記録のみ） |
| `rtt` | object | クライアント側の RTT 表示用。判定には使わない |

**サーバーが弾くのは `R < R_min` だけ**（SET2-4 §5.3 で整合性検査を廃止）。
`residual = serverElapsed − R − serverRtt.median` は引き続き算出して CSV と `RESULT` に残すが、
**判定には使わない**。計測が健全かを見るための診断値。

### 4.4 `RESULT` の中身

```
{
  type: "RESULT", matchId, roundId, resultId,
  reason: "反応が速い",
  recorded: true,          // false なら戦績に計上しない（SET2-6 へのフラグ）
  players: [
    { id, name, result: "win"|"lose"|"draw"|"void",
      R,                          // 申告値。そのまま判定に使う
      flying, tooFast, noInput, disconnected,
      serverElapsed, residual }   // 診断値。判定には使わない
  ]
}
```

## 5. 重複・順序逆転・古い入力

### 5.1 捨てる条件

サーバーは次のいずれかに当てはまる `TAP` を**黙って捨てる**（エラーも返さない）。

| 条件 | 理由 |
|---|---|
| `matchId` が現在のルームと不一致 | 別マッチ宛の迷子 |
| `roundId` が現在のラウンドと不一致 | 古いラウンド宛。再接続直後に起きる |
| 送信元がそのルームの参加者でない | 第三者の割り込み |
| そのラウンドで既に `TAP` を受理済み | 連打（ケース12）。`extraTaps` だけ加算 |
| ラウンドが既に `RESOLVED` | 判定後の到着 |

**エラーを返さない理由**: 返すと「今どの状態か」「誰が参加しているか」が外から探れる。
また `roundId` 不一致のエラーは、総当たりで有効な `roundId` を見つける手がかりになる。

### 5.2 `eventId` の使い方

クライアントは接続ごとに `eventId` を 1 から連番で振る。
サーバーは接続ごとに「最後に処理した `eventId`」を保持し、それ以下の値を再処理しない。

これは**再送による二重処理を防ぐため**であって、順序保証ではない。
WebSocket は同一接続内の順序を保つので、並べ替えは考えなくてよい。
再接続すると `eventId` はリセットされるが、`matchId` / `roundId` の検査が効くので問題ない。

### 5.4 RTT をクライアントに測らせてはいけない（実装中に発見）

整合性検査は次の式で成り立っている。

```
residual = serverElapsed − R − RTT
```

`serverElapsed` はサーバーが測るので偽れない。しかし **`R` と `RTT` の両方をクライアントが握っていると、
検査は無力化する**。`R` を小さく偽ったぶんだけ `RTT` を大きく申告すれば、`residual` はいくらでも 0 に寄せられる。

```
実際: 400ms でタップ、RTT 1ms
偽装: R = 120ms と申告し、RTT = 300ms と申告
      residual = 400 − 120 − 300 = −20  →  ε=80 を通過してしまう
```

**RTT はサーバーが自分で測る。** サーバーが `SPING` を送り、`SPONG` の往復時間を記録する。
クライアントの `rtt` フィールドは画面表示と診断のためだけに残し、判定には一切使わない。

これは E2E テストを書いていて見つかった。core の単体テストだけでは、
`rtt` を誰が測っているかという問いが出てこなかった。

### 5.3 順序逆転が起きる唯一の経路

同一接続内では起きない。起きるのは**再接続をまたいだとき**だけ。

```
旧接続で TAP 送信 → 切断 → 再接続 → 新接続で TAP 送信 → 旧接続の TAP が遅れて到着
```

旧接続の `TAP` は、サーバーが旧接続を閉じた時点で破棄する。
接続が閉じた後に届いたフレームは読まない。

## 6. 結果を一度だけ確定させる

### 6.1 二重確定の防止

ラウンドオブジェクトに `resolved` フラグを持ち、`resolveRound()` の冒頭で確認して即 return する。

判定が走る契機は3つあり、**同時に発火し得る**。

1. 双方の `TAP` が揃った
2. 入力期限 `T` のタイマーが発火した
3. どちらかが切断した

例えば「期限ぎりぎりに両者の `TAP` が届き、同時にタイマーが発火する」は普通に起きる。
`resolved` フラグと、判定時の**タイマー解除**（`clearTimeout`）の両方が要る。

### 6.2 二重保存の防止

`RESULT` には `matchId` + `roundId` から決まる**結果ID**を持たせ、SET2-6 側はそれを一意キーにする。

```
resultId = `${matchId}:${roundId}`
```

同じ `resultId` の書き込みが2回来たら2回目を捨てる。
クライアントから勝敗を直接書き込ませない（SET2-6 の要件）。

### 6.3 `recorded` フラグ

判定結果とは独立に「戦績に計上してよいか」を返す。

| `recorded` | 条件 |
|---|---|
| `false` | 無効試合（ケース7・双方切断）、信用検査で `R` を差し替えたラウンド（ケース10・11） |
| `true` | それ以外 |

## 7. 第三者の参加・入力を拒否する

| 攻撃 | 対策 |
|---|---|
| 他人のルームに割り込む | ルームの参加者リストは**サーバーが作る**。クライアントから `matchId` を指定して参加させない |
| `matchId` を推測して `TAP` を送る | 送信元 `clientId` が参加者かを毎回確認する。`matchId` が当たっても弾かれる |
| 3人目が接続する | ルームの定員は2。超えたら `ERROR` で閉じる |
| 相手の `clientId` を騙る | `clientId` は接続から引く。メッセージ中の自己申告は**一切信用しない** |

`MATCHED` で相手の `clientId` を渡さないのは、騙りの材料を減らすため。表示名だけで足りる。

## 8. ルームのライフサイクル

### 8.1 破棄の条件

| 条件 | 動作 |
|---|---|
| 双方が `LEAVE` または切断 | 即座に `CLOSED`、ルーム削除 |
| `RESOLVED` 後、一定時間（案: 60秒）どちらも `READY` を送らない | `CLOSED`、ルーム削除 |
| `WAITING` のまま一定時間（案: 120秒）進展しない | `CLOSED`、ルーム削除 |

**タイマーは必ずルーム削除時に解除する。** 解除し忘れると、削除済みルームを参照するコールバックが残る。
プロトタイプでは `goTimer` と `deadlineTimer` を `resolveRound()` で解除している。

### 8.2 再接続

MVP では**ラウンド中の再接続で復帰させない**。切断はケース7・8 で決着する。

再接続したクライアントには `WELCOME` → 新しいマッチング（SET2-3）を返す。
「同じマッチに戻る」機能は、匿名セッションの同一性を判定できない以上（SET2-7 の限界）実装しない。

## 9. 技術候補の比較

**一次資料で確認した日: 2026-09-12。** 仕様は変わるので、実装着手時に再確認すること。

### 9.1 候補

| | Node + ws（現行プロトタイプ） | Cloudflare Workers + Durable Objects | Socket.IO | Colyseus |
|---|---|---|---|---|
| 実装量 | **済**（12ケース検証済み） | 書き直し。ゲーム処理は約200行 | ws からの移行は小 | 大。フレームワークに合わせる |
| 運用 | プロセスを常駐させるホストが要る | **サーバー管理不要** | Node と同じ | Node と同じ |
| HTTPS/WSS | 証明書とドメインの用意が要る | **`workers.dev` で無料で付く** | — | — |
| 費用 | ホスト代 | **無料枠で足りる**（§9.2） | ホスト代 | ホスト代 |
| 1ルーム=1インスタンス | 自前で Map 管理 | **DO がそのままルーム**。設計と一致 | 自前 | Room が組み込み |
| 余計な機能 | なし | なし | 再接続・ロングポーリング fallback | 状態同期・スキーマ |

### 9.2 Durable Objects の無料枠（確認済み）

- Durable Objects は 2025年4月から **Workers 無料プランで利用可能**。ただし **SQLite バックエンドのみ**
- 無料プランのストレージ上限は 1 DO あたり 1GB、アカウント合計 5GB
- Workers 無料プランは **1日 100,000 リクエスト**、**呼び出しあたり CPU 10ms**
- **WebSocket は最初の Upgrade だけがリクエスト1回として数えられ、その後のメッセージは数えられない**

最後の点が効く。1日10万接続まで無料で、対戦中のメッセージは課金対象外。趣味プロジェクトには十分すぎる。
本件の CPU 使用量は数値比較だけなので 10ms 制限も問題にならない。

### 9.3 Durable Objects の懸念（重要）

**デプロイ後の Workers では `Date.now()` と `performance.now()` が I/O のたびにしか進まない。**
Spectre 対策で、コード実行中は時刻が固定される。

本件はサーバー側の経過時間 `serverElapsed = tapRecvAt − goSentAt` が整合性検査の土台なので、
ここが壊れると SET2-4 の設計が成立しない。

理屈の上では問題ないはず。`goSentAt`（GO 送信）も `tapRecvAt`（TAP 受信）も I/O イベントの時点で
読むので、その間に I/O は挟まっている。しかし**「はず」であって未検証**。

さらに厄介なことに、**ローカル開発では時刻が通常どおり進む**ため、
`wrangler dev` でいくらテストしても、この問題は発見できない。

> **DO を採用する場合の必須タスク**: デプロイ環境で `serverElapsed` が実時間と一致するかを実測する。
> ローカルでの動作確認は根拠にならない。

もうひとつ、**`setTimeout` / `setInterval` は hibernation を妨げる**。
本件は待機 `W`（1〜4秒）と期限 `T`（3秒）でタイマーを使うため、対戦中は hibernation されない。
1試合が数秒なので実害はないが、「待機列で延々アイドルするルーム」を DO で持つ設計にすると効いてくる。

### 9.4 Socket.IO と Colyseus を採らない理由

**Socket.IO**: 主な価値は再接続とトランスポート fallback。
本件は §8.2 のとおり**ラウンド中の再接続を復帰させない**方針なので再接続機能が要らない。
ロングポーリング fallback はむしろ有害で、遅延特性が変わると `residual` の基準値がずれる。

**Colyseus**: 状態同期とスキーマが主な価値。
本件の共有状態は「2人の反応時間」だけで、同期すべき連続状態がない。
フレームワークの分だけ、判定タイミングの制御が間接的になる。

どちらも「使わない理由」が明確なので候補から外す。

### 9.5 採用方針

**判定ロジックをトランスポート非依存のモジュールに切り出し、接続層だけをアダプタにする。**

```
core/match.js      … 状態遷移と判定。I/O を一切持たない純粋な関数群
adapters/node-ws.js … 現行プロトタイプ（ローカル開発・検証用）
adapters/durable-object.js … 本番候補
```

理由:
- ゲーム処理は約200行しかなく、切り出しのコストが小さい
- **kusa の組み込み要件（SET2-7）が未確認**な段階で本番プラットフォームを確定させるのは早い
- §9.3 の時刻問題を実測してから決められる。失敗しても Node + ws に戻せる

**当面は Node + ws で進める。** 既に動いていて検証済みであり、
時刻の扱いが素直（`performance.now()` が単調増加）で、SET2-4 の前提をそのまま満たす。

**デプロイ先を決める段になったら Durable Objects を第一候補とする。**
無料枠と `workers.dev` の HTTPS は、iframe 組み込みが必要な本件と趣味の予算によく合う。
ただし §9.3 の実測を通すことが条件。

## 10. SET2-3・SET2-5 と共有する取り決め

**SET2-3（マッチメイキング）へ**
- ルームを作るのは SET2-3。作った時点で `matchId` を発行し、両者に `MATCHED` を送る
- 1つの `clientId` が同時に所属できるルームは1つ。待機列と対戦の二重所属を防ぐ
- ルームが `CLOSED` になったら SET2-3 に通知し、待機列へ戻せるようにする

**SET2-5（UI/演出）へ**
- 画面が反応すべきサーバーイベントは `MATCHED` / `ARMED` / `GO` / `RESULT` / `PEER_LEFT` の5つ
- `ARMED` に待機時間 `W` を含めない。含めると待ち時間が読めてフライングし放題になる
- フライングした瞬間に相手へ知らせない。`RESULT` まで伏せる
- `recorded: false` のとき「この試合は記録されません」と出す。**不正とは書かない**

**SET2-6（戦績）へ**
- 一意キーは `resultId = matchId:roundId`。同じキーの2回目の書き込みは捨てる
- `recorded: false` のラウンドは集計に入れない
- クライアントから勝敗を直接書き込ませない
