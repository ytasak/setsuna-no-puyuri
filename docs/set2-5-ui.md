# SET2-5 UI/演出：🥺を中心に短い対戦体験を設計する

> ステータス: **ドラフト**
> 対応チケット: [SET2-5](https://linear.app/setsuna-no-puyuri/issue/SET2-5)
> 前提: [SET2-4 判定方式](./set2-4-sync-fairness.md)（確定）、[SET2-2 状態遷移・メッセージ仕様](./set2-2-realtime-match.md)（確定）

## 1. 参考にする体験

**星のカービィの「刹那の見切り」**（居合の早押しミニゲーム）を参考にする。
あの体験が成立している理由を分解すると、本件と同じ構造を持っている。

| 借りるもの | なぜ効くか |
|---|---|
| **静けさで溜める** | 待機中に何も起きないほど、合図の一瞬が刺さる。演出を足すのではなく引く |
| **合図は単一の記号** | 「なにか起きた」ではなく「**あれ**が出た」と分かる。判断が速くなる |
| **決着が一瞬で二値** | 勝ちか負けか。曖昧な中間状態を見せない |
| **反応時間を数値で出す** | 「次はもっと速く」の動機になる。1試合が短いので即再挑戦できる |
| **フライングが即座に分かる** | 早く押したら負け、という規則が体験として刻まれる |

**借りないもの**: キャラクター、スプライト、効果音・音楽、和風・侍のトレードドレス、
および「刹那の見切り」という名称そのもの。

本作の画面は **🥺 だけ**で構成する。侍や刀を持ち込まない。
これは権利面で安全なだけでなく、kusa コミュニティの文脈（🥺＝ぷゆゆ）にも合っている。

> タイトル「刹那のぷゆり」が元ネタを想起させる点は、公開前に SET2-8 で扱う。
> 趣味の小品として問題になる可能性は低いが、判断材料として記録しておく。

## 2. 画面状態

SET2-2 のサーバーイベントと1対1で対応させる。**クライアントは状態を勝手に進めない。**

| # | 状態 | 契機 | 画面 | 入力 |
|---|---|---|---|---|
| 1 | 接続中 | 起動 | 暗転＋「接続しています」 | 無効 |
| 2 | ルール確認 | `WELCOME` | ルール文＋「はじめる」 | 開始のみ |
| 3 | 相手待ち | `STATE` | 「相手を探しています」 | 中止のみ |
| 4 | 準備確認 | `MATCHED` | 相手表示＋「準備する」 | 準備のみ |
| 5 | **合図待ち** | `ARMED` | **完全に静止した暗い画面＋「まだ」** | **全画面**（押すとフライング） |
| 6 | **合図** | `GO` | **明転＋中央に巨大な🥺** | **全画面** |
| 7 | 送信済み | 自分の入力後 | 「相手を待っています」 | 無効 |

> 合図が出たら、すぐ押す。
> 合図の前に押すと負け。

## 3. 合図待ち（状態5）— ここが設計の核

完了条件「待機アニメーションや音が合図を先に知らせない」を満たすための決まりごと。

### 3.1 やってはいけないこと

| 禁止 | 理由 |
|---|---|
| カウントダウン | 終わりが読める。反応ではなく予測の勝負になる |
| プログレスバー・ゲージ | 同上。残り時間が見える時点で失格 |
| 合図の直前に何かを変える（溜め演出） | **それ自体が合図になる**。本当の合図より前に情報が出る |
| 待機時間 `W` をクライアントに渡す | SET2-2 §4.2 で禁止済み。UI 側でも使わない |
| 待機中の音 | 音の変化が手がかりになる。また音は遅延が端末依存 |

### 3.2 採る方針: **何も動かさない**

合図待ちの画面は**完全に静止**させる。アニメーションを一切置かない。

これは消極的な選択ではなく、参考にした体験の核心そのものである。
画面が静かであるほど、合図の一瞬が強く出る。
同時に「先読みの手がかりを作らない」という要件も自動的に満たせる。

画面: ほぼ黒の背景、中央に小さく「まだ」。それだけ。

### 3.3 合図の描画（状態6）

**CSS の transition / animation を使ってはいけない。**

SET2-4 は `t_display ≈ t_paint + フレーム間隔` で反応時間を測っている。
フェードインで合図を出すと「いつ表示されたか」が定義できなくなり、この推定が崩れる。

```
GO受信 → requestAnimationFrame 1回の中で、合図の表示を完了させる
        → その rAF のタイムスタンプが t_paint
```

- 背景を暗→明に**一段で**反転
- 中央に🥺を**最大サイズで即座に**表示
- 途中の状態を作らない

### 3.4 色だけに頼らない

完了条件「色や音だけに頼らず合図と結果を識別できる」への対応。

合図は**3つの手がかりが同時に変わる**ので、どれか1つが使えなくても伝わる。

1. **形**: 🥺 が無い → ある（最大の手がかり）
2. **明度**: 暗い → 明るい（色相ではなく明度差なので色覚に依存しない）
3. **文字**: 「まだ」→「いま」

音は使わない。音なし環境が前提（SET2-2 の対象は iframe 内の Web）。

## 4. 入力

### 4.1 受け付けるもの

| 入力 | イベント | 備考 |
|---|---|---|
| タップ・クリック・ペン | `pointerdown` | これを正とする |
| キーボード | `keydown`（Space / Enter） | `repeat` は無視 |

`click` は使わない。`pointerdown` と二重に発火するため。
`touchstart` も使わない。`pointerdown` が統一的に拾う。

時刻は `PointerEvent.timeStamp` を使う（SET2-4 §2.1）。
ハンドラ実行時刻より、入力そのものの時刻に近いため。

### 4.2 入力領域は画面全体

ボタンを狙わせない。**狙う時間が反応時間に混ざる**。
合図待ちと合図の状態では、画面のどこを押しても入力として扱う。

結果画面（状態8）で全画面タップを「もう一度」にすると、
合図の勢いで押した指がそのまま次に進めてしまう。
**結果表示から一定時間（案: 600ms）は入力を受け付けない。**

### 4.3 二重入力と連打

- 1ラウンドで採用するのは最初の1回だけ（SET2-2 ケース12）
- 2回目以降はクライアントで数えるだけで送らない
- 送信後は状態7に移り、入力を無効化する

## 5. 結果表示（状態8）

完了条件「各状態で何をすべきか、勝敗理由、再参加方法が分かる」への対応。

### 5.1 出すもの

```
        勝ち / 負け / 引き分け          ← 大きく。記号（○ × －）も添える
        ─────────────────
        あなた   182 ms
        あいて   214 ms                 ← 数値を出す。再挑戦の動機になる
        ─────────────────
        （敗因・注記）
                                        ← 600ms 後に「もう一度」
```

### 5.2 敗因の文言

| 状況 | 文言 |
|---|---|
| 反応時間で負けた | 「わずかに遅かった」 |
| フライング | 「合図の前に押した」 |
| 反応が速すぎる（`R < R_min`） | 「合図より前に反応している」 |
| 相手が無入力 | 「あいてが押さなかった」 |
| 自分が無入力 | 「押せなかった」 |
| 切断で負けた | **「通信が切断されました」** |
| 同着 | 「ほぼ同時」 |

### 5.3 信用検査に関わる文言（SET2-4 §5.1 と共有）

| 条件 | 文言 |
|---|---|
| `Rsource === 'server-estimate'` | 「この端末の計測値は使われませんでした」 |
| `recorded === false` | 「この試合は記録されません」 |

**どちらも不正とは書かない。** 端末の性能不足・回線の瞬断・OS の割り込みでも同じ症状が出る。
断定するとほぼ確実に誤検知で苦情になる。

### 5.4 フライングした本人への表示

フライングした瞬間、**本人には**「早すぎた」と出してよい。
**相手には知らせない**（SET2-2 §3.1: 知らせると相手が合図を待たずに押せる）。

本人も状態7（相手を待っています）に移り、`RESULT` が来るまで結果は確定しない。

## 6. iframe・モバイルでの制約

完了条件「iframe 内で操作領域が欠けず、スクロールや入力重複が判定を壊さない」への対応。

| 課題 | 対応 |
|---|---|
| iframe の高さが不定 | `100vh` / `100dvh` を使わず、`html,body{height:100%}` で親に追従させる |
| スクロールで入力位置がずれる | `overflow:hidden`、`overscroll-behavior:none` |
| スクロール判定で入力が遅れる | 入力領域に `touch-action:manipulation` |
| ダブルタップズーム | `touch-action:manipulation` で抑制。viewport でも `user-scalable=no` |
| 長押しメニュー・テキスト選択 | `user-select:none`、`-webkit-touch-callout:none` |
| 狭い幅（~320px） | 相対単位のみ。`clamp()` で文字サイズを可変に |
| 横向き・低い高さ | 縦積みをやめて中央1カラムに寄せる。要素数を増やさない |
| 動きを減らす設定 | `prefers-reduced-motion` で結果演出を簡略化。合図はもともと無アニメーション |

**iframe 内でのタイマー精度は未確認**（SET2-4 §2.1、SET2-7 の確認待ち）。
実際に kusa へ埋め込んだ状態で `performance.now()` の分解能を測り直すこと。

## 7. SET2-4 の計測と整合させる

UI 側が守らないと計測が壊れる点をまとめる。

1. **合図の描画は rAF 1回で完了させる**（§3.3）。transition を挟むと `t_display` が定義できない
2. **`t_input` は `PointerEvent.timeStamp` を使う**。ハンドラ実行時刻を使わない
3. **`t_display = t_paint + フレーム間隔` の推定に合わせる**。合図を描く rAF のタイムスタンプが `t_paint`
4. **合図待ちで一切アニメーションしない**。rAF を占有すると描画が遅れ、`t_recv → t_paint` が伸びる
5. **バックグラウンド化を検出して送る**。`visibilityState` が `hidden` になったラウンドは信用検査で弾かれる

## 8. プロトタイプ

`experiments/reaction-lab/public/game.html` で遊べる。サーバーは同じ `npm start`。

```
http://localhost:8787/game.html?room=play&name=じぶん
```

同じ `room` を2つ開くと対戦になる。`/` は計測用の lab、`/game.html` がプレイ用。

### 実装して分かったこと

- **`hidden` 属性はクラスの `display` 指定に負ける。** `.times { display: grid }` があると
  `hidden` が効かず、合図の画面に前ラウンドの記録が残っていた。`[hidden] { display: none !important }` で対処
- **接続インジケータも合図待ち中は消す。** 合図の直前に何かが変われば、それ自体が手がかりになる。
  常時表示している要素はすべて「合図の瞬間に変化しないか」を確認すること

### iframe 埋め込みでの確認

`/embed-test.html` で、狭い枠に埋め込んだ状態を並べて見られる。

| 枠 | 横スクロール | 縦スクロール | 操作領域 | ボタン高さ |
|---|---|---|---|---|
| 360 × 540 | なし | なし | 360 × 540（枠いっぱい） | 57px |
| 320 × 420 | なし | なし | 320 × 420（枠いっぱい） | 57px |
| 560 × 300（横長） | なし | なし | 560 × 300（枠いっぱい） | 48px |

完了条件「iframe 内で操作領域が欠けず、スクロールや入力重複が判定を壊さない」を満たしている。
タップ領域は最小 48px を確保。

**ただし kusa の実際の埋め込み条件は未確認**（SET2-7 待ち）。
sandbox 属性の指定によっては挙動が変わる可能性がある。
