# SET2-5 UI/演出：🥺を中心に短い対戦体験を設計する

> ステータス: **ドラフト**
> 対応チケット: [SET2-5](https://linear.app/setsuna-no-puyuri/issue/SET2-5)
> 前提: [SET2-4 判定方式](./set2-4-sync-fairness.md)（確定）、[SET2-2 状態遷移・メッセージ仕様](./set2-2-realtime-match.md)（確定）

## 1. 参考にする体験

**星のカービィの「刹那の見切り」**（居合の早押しミニゲーム）を参考にする。
あの体験が成立している理由を分解すると、本件と同じ構造を持っている。

| 借りるもの | なぜ効くか |
|---|---|
| **静けさで溜める** | 待機中に何も起きないほど、合図の一瞬が刺さる。演出を足すのではなく引く |
| **合図は単一の記号** | 「なにか起きた」ではなく「**あれ**が出た」と分かる。判断が速くなる |
| **決着が一瞬で二値** | 勝ちか負けか。曖昧な中間状態を見せない |
| **反応時間を数値で出す** | 「次はもっと速く」の動機になる。1試合が短いので即再挑戦できる |
| **フライングが即座に分かる** | 早く押したら負け、という規則が体験として刻まれる |

**借りないもの**: キャラクター、スプライト、効果音・音楽、和風・侍のトレードドレス、
および「刹那の見切り」という名称そのもの。

本作の画面は **🥺 だけ**で構成する。侍や刀を持ち込まない。
これは権利面で安全なだけでなく、kusa コミュニティの文脈（🥺＝ぷゆゆ）にも合っている。

> タイトル「刹那のぷゆり」が元ネタを想起させる点は、公開前に SET2-8 で扱う。
> 趣味の小品として問題になる可能性は低いが、判断材料として記録しておく。

| # | 状態 | 契機 | 画面 | 入力 |
|---|---|---|---|---|
| 1 | 接続中 | 起動 | 暗転＋「接続しています」 | 無効 |
| 2 | ルール確認 | `WELCOME` | ルール文＋「はじめる」 | 開始のみ |
| 3 | 相手待ち | `STATE` | 「相手を探しています」 | 中止のみ |

## 3. 合図待ち（状態5）— ここが設計の核

完了条件「待機アニメーションや音が合図を先に知らせない」を満たすための決まりごと。

### 3.1 やってはいけないこと

| 禁止 | 理由 |
|---|---|
| カウントダウン | 終わりが読める。反応ではなく予測の勝負になる |
| プログレスバー・ゲージ | 同上。残り時間が見える時点で失格 |
| 合図の直前に何かを変える（溜め演出） | **それ自体が合図になる**。本当の合図より前に情報が出る |
| 待機時間 `W` をクライアントに渡す | SET2-2 §4.2 で禁止済み。UI 側でも使わない |
| 待機中の音 | 音の変化が手がかりになる。また音は遅延が端末依存 |

### 3.2 採る方針: **静止させる。ただし空白にはしない**

> **2026-09-13 訂正。** 当初は「合図待ちの画面には何も置かない」としていたが、これは行きすぎだった。
> 真っ黒な画面に「まだ」だけでは、先読みの手がかりは無い代わりに**緊張感も無い**。
>
> 参考にした体験の待機画面は空白ではない。**二人が向かい合って対峙している。**
> 緊張は「情報が無いこと」からではなく、**対峙していることから**生まれる。
> そして対峙の構図は静止しているので、合図の時刻を何も漏らさない。
>
> 制約は「合図の時刻を予告しない」であって「何も映さない」ではない。両者は両立する。

### 舞台

元ネタと同じく、**一枚絵の横構図**で舞台を作る。

```
        ○ 月
                            空（夜 → 地平線へ向かって夕焼け）
        ぷゆ！              ← 合図はここ。画面の中央
   🥺        🥺             ← 二人は地平線に立つ
  あなた     あいて
────────────────────  地平線
        対 峙                地面（ここが HUD）
       ［構える］
```

- 空と地面の2段構成。**地平線の上に二人が立つ**
- 空は夜から地平線に向かって夕焼けに変わる。月をひとつ置く
- 高さに追従させる（地面の高さを内容で決め、空が残りを埋める）。iframe の高さが不定でも崩れない

背景の要素:

| 要素 | 内容 | 動き |
|---|---|---|
| 星 | 空に散らした点。CSS の `radial-gradient` を重ねるだけで DOM を増やさない | ゆっくり瞬く |
| 雲 | ぼかした横長の楕円を3つ、横に流す | 90秒かけて流れる |
| 山 | 稜線を遠近2枚の SVG で重ねる。遠い方は薄く、近い方は濃く | **動かない** |
| 草 | 地平線に沿った草。奥（細く低い）と手前（太く高い）の2層 | 風になびく |

### 書体

見出しは筆書体で太く出す。**Reggae One**（Google Fonts）を採用した。

| 用途 | 書体 |
|---|---|
| 合図「ぷゆ！」、勝敗、「対 峙」「ま だ」、タイトル、ボタン | Reggae One（筆・太字） |
| 反応時間の数値、説明文、注記 | システムフォント（等幅数字と可読性を優先） |

候補は `Yuji Boku`（墨・筆だが細い）、`Yuji Syuku`（筆・細身）、`Shippori Mincho B1 800`（太明朝）、
`Kaisei Decol 700`（太丸）と並べて比較した（`/font-test.html` に残してある）。
**筆感と太さを両立していたのが Reggae One** だった。

合図は輪郭の影を8方向に重ねて、さらに太らせている。

読み込めなかった場合は `Klee One` → ヒラギノ明朝 → 游明朝 → serif に落ちる。

**書体が載りきるまで「構える」を受け付けない。** 読み込み中にラウンドが始まると、
合図の字形が途中で入れ替わって描画が遅れかねないため（`document.fonts.ready` で待つ）。

### 風が止まる

**構えた瞬間（`ARMED`）に、草も雲も星の瞬きも止まる。**

合図待ちで動くものを残すと、rAF を占有して合図の描画が遅れかねない（§7.4）。
だが「合図待ちでは何も動かさない」を守りつつ、それ以外の場面では舞台を生かしたい。
そこで**構えた瞬間に風を止める**ことにした。

- 制約を満たす: 合図待ちの間、画面上で動くものは何も無い
- 手がかりにならない: 止まるのは `ARMED` の瞬間であって、合図の直前ではない
- **むしろ緊張が増す**: 構えた途端に世界が静止する

制約への対処が、そのまま演出になった例。

合図待ちの画面:

- 二人の 🥺 が**向かい合う**（相手側は左右反転）。暗く沈めて、まだ抜いていない状態を表す
- わずかに前傾させて**構え**を出す。ただし**静止**させたままで、動かさない
- **一切動かさない。** アニメーションも、点滅も、脈動も置かない

動かさない理由は2つある。ひとつは合図の直前に何かが変われば、それ自体が合図になるため。
もうひとつは rAF を占有すると合図の描画が遅れ、`t_recv → t_paint` が伸びるため（§7.4）。

### 3.3 合図は対峙を崩さず、画面の中央に出す

**対峙の構図はそのまま維持する。** 二人を消して別の画面に切り替えるのではなく、
**向かい合ったままの二人のあいだ、画面の中央に合図が出る。**

合図の文字は **「ぷゆ！」**。

同時に変わるのは3つ。

1. **中央に「ぷゆ！」が出る**（無 → 有）
2. **舞台が一段明るくなる**（空・地面・月がまとめて明るくなる）
3. **二人が明るくなる**（沈んでいた色が戻る）

### 3.3.1 合図の描画（状態6）

**CSS の transition / animation を使ってはいけない。**

SET2-4 は `t_display ≈ t_paint + フレーム間隔` で反応時間を測っている。
フェードインで合図を出すと「いつ表示されたか」が定義できなくなり、この推定が崩れる。

```
GO受信 → requestAnimationFrame 1回の中で、合図の表示を完了させる
        → その rAF のタイムスタンプが t_paint
```

- 背景を暗→明に**一段で**反転
- 中央に🥺を**最大サイズで即座に**表示
- 途中の状態を作らない

### 3.4 決着の演出は自由にしてよい

**合図より後は計測に一切影響しない。** ここが演出の置き場所になる。

| 段階 | 演出 |
|---|---|
| 閃光 | 画面全体が白く飛ぶ（340ms で落ちる） |
| 斬撃 | 地平線に沿って**光の刃が3本**走る。太い本命＋細い2本を少しずらして重ねる。勝った側から負けた側へ向かう |
| 震動 | 舞台全体が揺れる（360ms） |
| 決着 | 敗者の 🥺 が**回転しながら吹き飛ぶ**（620ms、画面外へ）。勝者の 🥺 は**残心**で大きくなり、金色に発光する |
| 相打ち | どちらも吹き飛ばず、閃光と斬撃だけが走る |
| 勝敗 | 「○ 勝ち」が大きく叩きつけられる（scale 2.1 → 1） |
| 数値 | 両者の反応時間を並べる |

斬撃の向きは勝者に合わせて左右反転させる。自分が勝てば左から右へ、負ければ右から左へ走る。

**音は決着でだけ鳴らす。** 合図では鳴らさない。
端末ごとの音声遅延が読めず、視覚より先に音が出ると不公平になるため（§3.1）。
音は WebAudio で生成し、素材ファイルを持たない。オン/オフを切り替えられる。
斬撃音（帯域を絞ったノイズ）＋着弾音（低域のノイズ）＋勝敗の音階を重ねる。
音を切っていても、あるいは端末が無音でも、体験は成立する。

`prefers-reduced-motion` が指定されていれば、斬撃と転倒のアニメーションを止め、
結果の状態（倒れている／立っている）だけを静止画として見せる。

### 3.5 音（2026-09-14 方針変更）

当初は「合図では鳴らさない」としていた。端末ごとの音声遅延が読めず、
**視覚より先に音が出ると不公平になる**と考えたため。

**実測でこの前提は否定された。**

```
AudioContext.baseLatency    :  5.3 ms
AudioContext.outputLatency  : 24.0 ms
```

Web Audio は必ず出力バッファを経由するので、**音が視覚より先に出ることは構造的にない。**
測ったのは Mac Chrome 1台だけだが、バッファを挟む以上どの環境でも順序は変わらない。

`sound.cue()` の実行時間も測った。**中央値 0.2ms**（60Hz のフレーム予算 16.7ms の 1%）。
合図の描画フレームの中で呼んでも、描画を遅らせない。

#### 残る非対称

人間の単純反応時間は**聴覚のほうが視覚より速い**とされる（聴覚 ~140-160ms、視覚 ~180-200ms）。
差は 20〜40ms で、同着幅 `D = 20ms` より大きい。

つまり**音を切っている人が構造的に不利**になる。ただし音の出力遅延 24ms がこれを打ち消す方向に働くので、
差し引きの優位は小さいか、端末によっては消える。

**許容する。** 視覚の合図は十分に強く（舞台が明転＋中央に巨大な「ぷゆ！」）、音は上乗せ。
日次リセットの小品で、ここまで厳密にする必要はない。
既定は音ありなので、不利になるのはミュートした人だけ。

#### 音の設計

| 場面 | 音 | 構造 |
|---|---|---|
| 合図 | **ドンッ**（太鼓） | バチの当たる音（1800Hz、20ms）＋ 胴の鳴り（150→72Hz、240ms） |
| 決着 | **バシィ**（斬撃） | 割れ（2400Hz、18ms）＋ 打撃（低域、90ms）＋ 擦過（1800→4000Hz、400ms） |

**低音だけの太鼓にしてはいけない。** 低音は耳が「いつ鳴ったか」を捉えにくいので、
バチが皮を叩く高めの音を頭に一瞬だけ置く。実際の太鼓もこの2層でできている。
合図として使う以上、頭の鋭さは外せない。

胴の高さを 60Hz 台まで下げると本物には近いが、スマホのスピーカーでは再生されない。
少し高めに置いて、倍音で太さを補う。

#### 実装上の落とし穴

**`exponentialRampToValueAtTime(0.0001, ...)` を使うと、体感の長さが指定の 1/3 になる。**
-80dB 超の減衰になるため。-36dB まで落としてから線形に切ると、指定値がそのまま長さになる。
42ms 指定で実測 15ms しか鳴っていなかった。

**コンプレッサーを合図の音に挟んではいけない。** 一度試して実測したところ、
Web Audio の `DynamicsCompressor` の固有の先読み遅延（Chrome で約6ms）で
合図の頭が 0ms から 20ms 先にずれ、**0〜5ms の振幅が完全に消えた**。
音量を稼ぐために transient を犠牲にする処理なので、アタックがすべての合図音とは相性が最悪。
層を重ねて割れるなら、各層のゲインを下げること。

### 3.6 色だけに頼らない

完了条件「色や音だけに頼らず合図と結果を識別できる」への対応。

合図は**3つの手がかりが同時に変わる**ので、どれか1つが使えなくても伝わる。

1. **形と文字**: 画面の中央に **「ぷゆ！」** が出る（無 → 有。最大の手がかり）
2. **明度**: 舞台が一段明るくなる（色相ではなく明度差なので色覚に依存しない）
3. **色**: 沈んでいた二人に色が戻る

勝敗も色だけに頼らない。記号（○ × －）、文字、そして**倒れているか立っているか**の3つで示す。

**音は補助にとどめ、無音でも成立させる。** 職場や公共の場では音を出せない。
合図は形・明度・色の3つが同時に変わるので、音を切っても判断できる。

## 4. 入力

### 4.1 受け付けるもの

| 入力 | イベント | 備考 |
|---|---|---|
| タップ・クリック・ペン | `pointerdown` | これを正とする |
| キーボード | `keydown`（Space / Enter） | `repeat` は無視 |

`click` は使わない。`pointerdown` と二重に発火するため。
`touchstart` も使わない。`pointerdown` が統一的に拾う。

時刻は `PointerEvent.timeStamp` を使う（SET2-4 §2.1）。
ハンドラ実行時刻より、入力そのものの時刻に近いため。

### 4.2 入力領域は画面全体

ボタンを狙わせない。**狙う時間が反応時間に混ざる**。
合図待ちと合図の状態では、画面のどこを押しても入力として扱う。

結果画面（状態8）で全画面タップを「もう一度」にすると、
合図の勢いで押した指がそのまま次に進めてしまう。
**結果表示から一定時間（案: 600ms）は入力を受け付けない。**

### 4.3 二重入力と連打

- 1ラウンドで採用するのは最初の1回だけ（SET2-2 ケース12）
- 2回目以降はクライアントで数えるだけで送らない
- 送信後は状態7に移り、入力を無効化する

## 5. 結果表示（状態8）

完了条件「各状態で何をすべきか、勝敗理由、再参加方法が分かる」への対応。

### 5.1 出すもの

```
        勝ち / 負け / 引き分け          ← 大きく。記号（○ × －）も添える
        ─────────────────
        あなた   182 ms
        あいて   214 ms                 ← 数値を出す。再挑戦の動機になる
        ─────────────────
        （敗因・注記）
                                        ← 600ms 後に「もう一度」
```

### 5.2 敗因の文言

| 状況 | 文言 |
|---|---|
| 反応時間で負けた | 「わずかに遅かった」 |
| フライング | 「合図の前に押した」 |
| 反応が速すぎる（`R < R_min`） | 「合図より前に反応している」 |
| 相手が無入力 | 「あいてが押さなかった」 |
| 自分が無入力 | 「押せなかった」 |
| 切断で負けた | **「通信が切断されました」** |
| 同着 | 「ほぼ同時」 |

### 5.3 信用検査に関わる文言（SET2-4 §5.1 と共有）

| 条件 | 文言 |
|---|---|
| `recorded === false` | 「この試合は記録されません」 |

**不正とは書かない。** 端末の性能不足・回線の瞬断・OS の割り込みでも同じ症状が出る。
断定するとほぼ確実に誤検知で苦情になる。

### 5.4 フライングした本人への表示

フライングした瞬間、**本人には**「早すぎた」と出してよい。
**相手には知らせない**（SET2-2 §3.1: 知らせると相手が合図を待たずに押せる）。

本人も状態7（相手を待っています）に移り、`RESULT` が来るまで結果は確定しない。

## 6. iframe・モバイルでの制約

完了条件「iframe 内で操作領域が欠けず、スクロールや入力重複が判定を壊さない」への対応。

| 課題 | 対応 |
|---|---|
| iframe の高さが不定 | `100vh` / `100dvh` を使わず、`html,body{height:100%}` で親に追従させる |
| スクロールで入力位置がずれる | `overflow:hidden`、`overscroll-behavior:none` |
| スクロール判定で入力が遅れる | 入力領域に `touch-action:manipulation` |
| ダブルタップズーム | `touch-action:manipulation` で抑制。viewport でも `user-scalable=no` |
| 長押しメニュー・テキスト選択 | `user-select:none`、`-webkit-touch-callout:none` |
| 狭い幅（~320px） | 相対単位のみ。`clamp()` で文字サイズを可変に |
| 横向き・低い高さ | 縦積みをやめて中央1カラムに寄せる。要素数を増やさない |
| 動きを減らす設定 | `prefers-reduced-motion` で結果演出を簡略化。合図はもともと無アニメーション |

**iframe 内でのタイマー精度は未確認**（SET2-4 §2.1、SET2-7 の確認待ち）。
実際に kusa へ埋め込んだ状態で `performance.now()` の分解能を測り直すこと。

## 7. SET2-4 の計測と整合させる

UI 側が守らないと計測が壊れる点をまとめる。

1. **合図の描画は rAF 1回で完了させる**（§3.3）。transition を挟むと `t_display` が定義できない
2. **`t_input` は `PointerEvent.timeStamp` を使う**。ハンドラ実行時刻を使わない
3. **`t_display = t_paint + フレーム間隔` の推定に合わせる**。合図を描く rAF のタイムスタンプが `t_paint`
4. **合図待ちで一切アニメーションしない**。rAF を占有すると描画が遅れ、`t_recv → t_paint` が伸びる
5. **バックグラウンド化を検出して送る**。`visibilityState` が `hidden` になったラウンドは信用検査で弾かれる

## 8. プロトタイプ

`experiments/reaction-lab/public/game.html` で遊べる。サーバーは同じ `npm start`。

```
http://localhost:8787/game.html?room=play&name=じぶん
```

同じ `room` を2つ開くと対戦になる。`/` は計測用の lab、`/game.html` がプレイ用。

### 実装して分かったこと

- **「引く」を徹底しすぎると緊張感まで消える。** 最初の実装は合図待ちを真っ黒な空白にしていたが、
  それでは対峙している感覚が無く、ただ待つだけの画面になっていた。
  **静止させることと、何も映さないことは違う。** 対峙の構図は静止しているので制約と両立する
- **演出の置き場所は合図より後。** 合図より前は一切動かせないが、決着は完全に自由。
  制約が厳しいのは合図の前だけだと気づけば、演出の予算をすべて決着に振り向けられる
- **`hidden` 属性はクラスの `display` 指定に負ける。** `.times { display: grid }` があると
  `hidden` が効かず、合図の画面に前ラウンドの記録が残っていた。`[hidden] { display: none !important }` で対処
- **接続インジケータも合図待ち中は消す。** 合図の直前に何かが変われば、それ自体が手がかりになる。
  常時表示している要素はすべて「合図の瞬間に変化しないか」を確認すること

### iframe 埋め込みでの確認

`/embed-test.html` で、狭い枠に埋め込んだ状態を並べて見られる。

| 枠 | 横スクロール | 縦スクロール | 操作領域 | ボタン高さ |
|---|---|---|---|---|
| 360 × 540 | なし | なし | 360 × 540（枠いっぱい） | 57px |
| 320 × 420 | なし | なし | 320 × 420（枠いっぱい） | 57px |
| 560 × 300（横長） | なし | なし | 560 × 300（枠いっぱい） | 48px |

完了条件「iframe 内で操作領域が欠けず、スクロールや入力重複が判定を壊さない」を満たしている。
タップ領域は最小 48px を確保。

**ただし kusa の実際の埋め込み条件は未確認**（SET2-7 待ち）。
sandbox 属性の指定によっては挙動が変わる可能性がある。
