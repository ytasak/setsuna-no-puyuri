# SET2-4 同期・公平性：合図・反応時間・不正対策の判定方式

> ステータス: **ドラフト（実測前）**
> 対応チケット: [SET2-4](https://linear.app/setsuna-no-puyuri/issue/SET2-4)
> この文書のうち「実測で決める値」は未確定。数値はすべて仮置きで、検証後に更新する。

## 1. この文書の目的

「合図が出たら先にタップした方が勝ち」を、**どの時刻を起点に、誰が計測し、何をもって勝敗とするか**を決める。
この判定方式が決まらないと SET2-2（状態遷移）・SET2-5（演出）・SET2-6（戦績）の設計が始められないため、
本チケットが実質のクリティカルパス起点になっている。

スコープ外:
- 通信基盤の技術選定（SET2-2）
- kusa からの識別情報の取得可否（SET2-7）
- ランキングを実際に公開するかの判断（SET2-6）。本書は「公開するなら何が必要か」の条件までを示す。

## 2. 時刻の定義

本件の議論が混乱する最大の原因は、**「合図」と呼ばれる時刻が4つある**こと。以下で厳密に区別する。

| 記号 | 名前 | 発生場所 | 取得方法 |
|---|---|---|---|
| `t_send` | サーバーが GO を送信した時刻 | サーバー | サーバーの単調時計 |
| `t_recv` | クライアントが GO を受信した時刻 | 端末 | `performance.now()`（WebSocket の message ハンドラ冒頭） |
| `t_paint` | 合図の描画処理が走った時刻 | 端末 | `requestAnimationFrame` コールバックの引数 |
| `t_display` | 実際に画面に出た時刻 | ディスプレイ | **直接は取得できない**（推定のみ） |

同様に入力側も2つある。

| 記号 | 名前 | 取得方法 |
|---|---|---|
| `t_input` | 入力イベントのハードウェアタイムスタンプ | `PointerEvent.timeStamp` |
| `t_handler` | JS のイベントハンドラが実行された時刻 | ハンドラ内の `performance.now()` |

**反応時間の定義**: `R = t_input − t_display`

`t_display` が取れない以上、`R` は常に推定値である。この事実を前提に方式を選ぶ。

### 2.1 各時刻の精度上の注意

- `performance.now()` は単調増加時計で、端末間の壁時計（wall clock）とは無関係。
  **端末Aの `performance.now()` と端末Bの `performance.now()` を直接比較してはならない。**
- タイマー精度は Spectre 対策で意図的に粗くされており、ブラウザと cross-origin isolation の状態によって
  概ね 0.1ms〜1ms 程度に丸められる。iframe 内での実値は **要実測**。
- `PointerEvent.timeStamp` は現代のブラウザでは `performance.now()` と同じ time origin を共有する
  高分解能タイムスタンプだが、iframe 内・ブラウザ差は **要実測**。`t_handler` より `t_input` を優先する
  （ハンドラ実行はメインスレッドの混雑で遅れるため）。
- `t_paint`（rAF コールバック引数）は「そのフレームのコールバック実行開始時刻」であって、
  画面に出た時刻ではない。合成とディスプレイ走査の分だけ後になる。
- したがって `t_display ≈ t_paint + (1 フレーム時間)` を推定に使う。60Hz なら約 16.7ms、120Hz なら約 8.3ms。
  **この差がそのまま端末間の系統的な有利不利になる**（§7.2）。

## 3. 方式の比較

### 方式A: クライアント計測・自己申告

サーバーは GO を push するだけ。端末が `R = t_input − t_display推定` を測り、値をサーバーに申告する。
サーバーは申告された `R` を比較して勝敗を決める。

- ✅ 回線遅延の影響を受けない。RTT 200ms のモバイル回線でも光回線と対等に戦える
- ❌ **クライアントの自己申告なので改ざんできる**。JS を書き換えて `R = 120` と送れば勝てる
- 実装量: 小

### 方式B: サーバー受信順

端末は GO 後に TAP を送るだけ。サーバーが TAP を受信した順序で勝敗を決める。

- ✅ 改ざん耐性が高い（申告値を使わない）
- ❌ **片道遅延の差がそのまま勝敗を決める**。人間の反応時間の個人差は概ね数十 ms のオーダーで、
  回線差はそれと同等かそれ以上になり得る。事実上「回線ゲー」になり、対戦として成立しない
- 実装量: 最小

### 方式C: ハイブリッド（方式A + サーバー側の整合性検査）

方式A を採用したうえで、サーバーが申告値の妥当性を検査する。

1. **生理的下限**: `R < R_min` は無効試合（§5, `R_min` は実測で決める）
2. **整合性**: 申告値 `R` と、サーバーが実際に TAP を受信した時刻の辻褄が合うかを検査する。
   `t_recv_tap − t_send ≈ (片道遅延) + R + (片道遅延)` が概ね成立するはずで、
   ここから大きく外れる申告を無効試合にする
3. **端末状態**: バックグラウンド化・異常なフレームレートを検出したら無効試合

- ✅ 公平性（方式Aの利点）を保ったまま、露骨な改ざんを弾ける
- ❌ **完全な不正防止にはならない**。「人間として自然な範囲の、少し速すぎる値」は検出できない。
  整合性検査も RTT 推定の揺らぎに依存するため厳密ではない
- 実装量: 中

### 3.1 採用案

**方式C を推奨する（ただし実測後に確定）。**

理由:
- 方式B は対戦の体を成さない。回線が良い側がほぼ常に勝つ設計は、カジュアル対戦として破綻している
- 方式A 単体は、ランキングを公開する場合に説明責任を果たせない
- 方式C の追加コストは検査ロジックのみで、方式A から段階的に強化できる

**やってはいけない設計**: 「未来の GO 時刻を事前に各端末へ配信し、時計を合わせて同時に表示する」方式。
同期精度は上がるが、**GO 時刻が事前に端末上に存在するため、その時刻ちょうどに自動入力するだけで必ず勝てる**。
GO はサーバーがランダム待機後に push し、事前に予告しない。

## 4. 計測フロー（方式C）

```
サーバー                              端末A / 端末B
   │
   │ 双方 READY を確認
   │ ランダム待機 W（§6）
   │
   ├── GO push ──────────────────────→ t_recv 記録
   │   t_send 記録                      │
   │                                    ├ rAF で合図を描画 → t_paint 記録
   │                                    │  t_display = t_paint + frame_time
   │                                    │
   │                                    ├ pointerdown → t_input 取得
   │                                    │  R = t_input − t_display
   │                                    │
   │←── TAP { R, 診断値 } ──────────────┤
   │   t_recv_tap 記録                   │
   │
   ├ 双方の TAP または入力期限 T の到達を待つ
   ├ 整合性検査（§3 方式C）
   ├ 判定（§5）
   └── RESULT push ──────────────────→ 結果表示
```

TAP に載せる診断値（整合性検査と分析に使う）:

| 項目 | 用途 |
|---|---|
| `R` | 申告された反応時間 |
| `t_recv − (GO受信の自端末時計)` の相対値 | GO受信から入力までの端末内経過時間 |
| 実効フレーム間隔 | ディスプレイのリフレッシュレート推定（§7.2） |
| `visibilityState` の履歴 | バックグラウンド化の検出 |
| GO 前の入力有無とその時刻 | フライング判定（§5） |

## 5. 判定規則ドラフト

`D` = 同着幅、`T` = 入力期限、`R_min` = 生理的下限。いずれも §6 で実測後に確定する。

| # | ケース | 条件 | 結果 |
|---|---|---|---|
| 1 | 正常 | 双方が GO 後 `T` 以内に入力し、`\|R_A − R_B\| > D` | `R` が小さい方の勝ち |
| 2 | 同着 | 双方が入力し、`\|R_A − R_B\| ≤ D` | 引き分け |
| 3 | フライング（片方） | 一方が `t_display` より前に入力 | **入力した側の負け** |
| 4 | 双方フライング | 双方が `t_display` より前に入力 | 引き分け |
| 5 | 片方無入力 | 一方だけが `T` 以内に入力 | 入力した側の勝ち |
| 6 | 双方無入力 | 双方が `T` を超過 | 引き分け（無効試合にはしない） |
| 7 | 切断（GO前） | 一方が GO 送信前に切断 | **無効試合**（戦績に計上しない） |
| 8 | 切断（GO後・入力前） | 一方が GO 後、入力前に切断 | 残った側の**不戦勝**（勝利として計上） |
| 9 | 申告値が下限未満 | `R < R_min` | **無効試合** |
| 10 | 整合性違反 | 申告値とサーバー受信時刻が矛盾（許容幅 `ε` 超過） | **無効試合** |
| 11 | バックグラウンド化 | GO 前後で `visibilityState` が `hidden` になった | **無効試合** |
| 12 | 連打 | 同一ラウンドで2回目以降の入力 | 無視（最初の入力のみ採用） |

### 5.1 「無効試合」と「不正」を分ける

ケース9・10・11 は **無効試合であって、不正の断定ではない**。

端末の性能不足、回線の瞬断、OS の割り込み、ブラウザの省電力動作でも同じ症状は起きる。
「不可能な時間だから不正」と断定してユーザーに提示すると誤検知で確実に苦情になるため、
UI 上は「この試合は記録されませんでした」とだけ伝える（SET2-5 と共有する仕様）。

累積的な傾向（同一セッションで無効試合が異常に多い等）をどう扱うかは SET2-6 の範囲。
匿名環境では継続的な排除ができないという限界も SET2-6 と共有する。

### 5.2 ケース4・8 の決定理由

どちらも実測とは無関係な、ゲームデザイン側の判断として確定した。

**ケース4（双方フライング）＝ 引き分け**

双方とも合図前に入力している時点で、どちらが先だったかを比べる意味がない。
「先にフライングした方の負け」にすると、フライング同士で 1ms を争う構図が生まれ、
「合図を待つ」というゲームの本旨から外れる。両者ペナルティの引き分けとし、再戦に進ませる。

**ケース8（GO後・入力前の切断）＝ 残った側の不戦勝**

**負けそうな局面での切断を、敗北回避の手段にしない**ための規則。
無効試合にすると「反応が遅れたと感じたら通信を切る」が最適戦略になり、対戦が壊れる。
残った側の勝利として計上する。

ただし、切断が本人の意図によるとは限らない（回線瞬断、バックグラウンド化によるソケット切断、
モバイル回線のハンドオーバー等）。切断した側には敗因を「通信が切断されました」と明示し、
不正として扱わない（§5.1 と同じ方針）。

なお、この規則は GO 後に限る。GO 前の切断（ケース7）は無効試合のままとする。
まだ勝負が始まっていないため、不戦勝を与える根拠がないことと、
マッチング直後の離脱は通常の離脱操作と区別できないことによる。

## 6. 実測で決める値

現時点ではすべて仮置き。**この表を埋めることが SET2-4 の完了条件そのもの。**

| 記号 | 意味 | 仮置き | 決め方 |
|---|---|---|---|
| `W` | GO までのランダム待機 | 1.0〜4.0 秒 | 短いとフライングが増え、長いと飽きる。体感で決める（SET2-5 と共同） |
| `T` | 入力期限（GO から） | 3.0 秒 | 「反応できなかった」と「切断」を分離できる長さ |
| `D` | 同着幅 | **20 ms（確定）** | `t_display` の推定誤差 ±8ms の約2倍。§10.5 で測定値から決定 |
| `R_min` | 生理的下限 | 100 ms | 単純視覚反応の下限は概ね 150ms 前後とされ、100ms 未満は予測入力とみなせる |
| `ε` | 整合性検査の許容幅 | 80 ms（要再検討） | 正直なプレイでも 60Hz で最大 31ms 出る（§10.5）。下げる余地はほとんどない |
| `frame_time` | 表示遅延の補正値 | 実効フレーム間隔 | 端末ごとに rAF 間隔から推定 |

## 7. 検証プロトコル

> **スコープ縮小（2026-09-12 決定）**
> 本プロジェクトは「ちょっとした遊び」であり、厳密さを追求しない。**検証は PC 端末のみで行う。**
> 以下のうち実機（iPhone / Android）での測定、非対称回線の実測、各条件30試行以上といった要求は
> **必須としない**。参考として残すが、やらずに先へ進んでよい。
> 不明な誤差は同着幅 `D` を広めに取って飲み込む方針とする。

### 7.1 計測系のばらつきを測る（`D` を決めるため）

同一端末・同一条件で GO → 入力を繰り返し、**同じ操作をしたときに `R` がどれだけばらつくか**を測る。
人間の反応そのもののばらつきと混ざらないよう、可能なら自動入力（スクリプトによる合成イベント）で計測系だけを切り出す。

測る値:
- `performance.now()` の実効分解能（連続呼び出しの差分の最小値）
- `t_recv → t_paint` の遅延分布
- rAF 間隔の分布（実効リフレッシュレート）
- `t_input → t_handler` の遅延分布（メインスレッド混雑の影響）

### 7.2 端末差を測る

| 端末 | ブラウザ | 想定リフレッシュレート |
|---|---|---|
| Mac | Chrome / Safari | 60Hz（外部ディスプレイ次第） |
| iPhone | Safari | 60Hz / 120Hz（ProMotion） |
| Android | Chrome | 60Hz / 90Hz / 120Hz |

**120Hz 端末は 60Hz 端末に対して、表示遅延で平均 4ms 程度、最大 8ms 程度の系統的な有利を持つ。**
これは技術的に解消できない。`D`（同着幅）をこの差より大きく取ることで実害を抑える方針とし、
残る不公平として §8 に記録する。

### 7.3 通信条件を変えて測る

| 条件 | 方法 |
|---|---|
| 同一LAN | そのまま |
| モバイル回線 | スマホのテザリング / 4G・5G |
| 片側だけ遅延注入 | Chrome DevTools のネットワークスロットリング、または macOS の `dummynet`（`pfctl`） |
| 非対称回線 | 上り下りで異なる帯域・遅延を設定 |

各条件で測る: RTT の中央値・p95・ジッタ、方式B を仮に採用した場合の勝率の偏り（方式B を棄却する根拠として記録）。

### 7.4 異常系

連打、GO 前の先押し、双方フライング、タブのバックグラウンド化、低フレームレート（別タブで重い処理）、
申告値の偽造（DevTools から改ざんした値を送る）を実際に試し、§5 の規則どおりに落ちることを確認する。

### 7.5 試行回数と記録

各条件 30 試行以上。結果は CSV で `experiments/` 配下に残し、集計結果を本書 §9 に追記する。

## 8. 残る限界（公開前に明示する）

SET2-8（審査資料）と SET2-6（ランキング公開判断）に引き渡す項目。

1. **自己申告値の改ざんは完全には防げない。** サーバー側検査で弾けるのは「明らかに不自然な値」だけで、
   人間として自然な範囲に収めた改ざんは検出できない。
   **検出下限はおよそ `ε` に等しい**（§10.2）。`ε = 80ms` なら、80ms 未満の上げ底は素通りする。
   反応時間を 200ms → 135ms に見せかける程度の不正は、この方式では原理的に検出できない。
   `ε` を小さくすれば検出力は上がるが、正直なプレイの `residual`（実測 8〜15ms、実回線ではさらに大きい）
   を誤って無効試合にし始める。**検出力と誤検知はトレードオフで、両立しない。**
2. **端末のリフレッシュレート差による系統的有利は解消できない。** 同着幅で緩和するのみ。
3. **整合性検査は RTT 推定に依存する。** 非対称回線では片道遅延を `RTT/2` と仮定できず、精度が落ちる。
4. **匿名環境では不正者を継続的に排除できない。** 別セッションを同一人物と断定する手段がない（SET2-3・SET2-6 と共通の限界）。
5. **`t_display` は推定値であり、真の表示時刻ではない。** 反応時間は常に誤差を含む。
6. **無効試合はグリーフィングの手段になる。** 無効試合は片方の違反で試合全体が無効になるため、
   勝てない相手に対して意図的に不正な申告を送れば、相手の勝ちを消し続けられる（§10.3）。
   偽造した側だけを負けにする案もあるが、それは「検査に引っかかった＝不正」と断定することであり、
   §5.1 の方針（端末不調と不正を区別できない）と衝突する。**現時点で綺麗な解はない。**

### 8.1 未決定事項

- 無効試合が続いたセッションの扱い（SET2-6 と調整）
- 無効試合を使ったグリーフィングへの対応（限界6）。SET2-6 の「不正申告・談合への対応方針」と同じ問題

ケース4（双方フライング）とケース8（GO後の切断）は決定済み。§5.2 を参照。

## 9. カジュアル許容範囲とランキング公開条件の線引き

完了条件の「カジュアル対戦としての許容範囲とランキング公開に必要な条件を区別する」への回答。

### カジュアル対戦（MVP の初期公開）

方式C の基本形で足りる。

- 同着幅 `D` を広めに取り、際どい勝負は引き分けにする
- 無効試合はユーザーに「記録されませんでした」とだけ伝える
- 不正は「弾けるものだけ弾く」。完全性を目指さない
- §8 の限界は、ゲーム内の説明文に平易な言葉で一行入れておく程度

### ランキングを公開する場合（SET2-6 の判断材料）

上記に加えて、最低限これらが必要になる。

1. 異常値の自動除外と、除外基準の明示
2. 端末情報（リフレッシュレート等）の記録。上位記録の成立条件を後から検証できるようにする
3. 上位記録の手動確認プロセス、および訂正・取り消しの手順
4. 複数匿名IDによる多重登録・談合への対応方針（対応できないなら、できないと明記する）

**それでも §8 の限界1・2は残る。** ランキングの正確性を保証することはできない。
SET2-6 では「保証できないランキングを公開するか」という形で判断することになる。

### 10.1 計測系の素の値

| 項目 | 実測 | 備考 |
|---|---|---|
| 実効リフレッシュレート | **120 Hz** | Mac の ProMotion。フレーム間隔 中央値 8.30ms / p95 9.10ms |
| `t_recv → t_paint` | 5.1 / 5.4 ms | GO 受信から描画処理までのメインスレッド遅延 |
| RTT（localhost） | 中央値 1.3〜1.4ms / p95 2.0〜2.6ms / ジッタ 0.46〜0.60ms | 実回線ではない下限値 |
| RTT（人工遅延 120ms） | 中央値 123.6ms / ジッタ 0.57ms | `delayUp=60&delayDown=60` |

フレーム間隔 p95 が中央値より 0.8ms しか大きくないので、少なくともこの端末では rAF は安定している。
**ただし 120Hz 端末しか測れていない。`D` の下限を出すには 60Hz 端末での測定が必須**（§7.2）。

### 10.2 整合性検査の実測

| ケース | 申告 `R` | 実タップ | `serverElapsed` | RTT | `residual` | 判定 |
|---|---|---|---|---|---|---|
| 正直・遅延なし | 200.5 | 200 | 216.98 | 1.3 | **15.18** | 正常 |
| 正直・遅延なし | 201.0 | 200 | 210.81 | 1.4 | **8.41** | 正常 |
| 正直・RTT 123ms | 230.6 | 230 | 366.30 | 123.4 | **12.30** | 正常 |
| **偽造** | 120.0 | 230 | 369.40 | 123.65 | **125.75** | 無効試合 |

正直なプレイの `residual` は **8〜15ms**。人工遅延 120ms を入れても増えていない
（RTT 中央値で引いているので当然だが、**ジッタが小さい条件でしか確かめていない**）。

**ここから分かる重要な制約**: 偽造の検出量は「実際のタップ時刻と申告値の差」そのものである。
上の例は 110ms 上げ底したので residual が 125ms になった。
**`ε = 80ms` なら、80ms 未満の上げ底は検出できない**（§8 限界1）。

### 10.3 走らせて分かった問題

**無効試合が両者に適用されるため、グリーフィングが成立する。**
上の偽造ラウンドでは、正直に 201ms で押した A も `void` になった。
つまり**勝てない相手は、偽造申告を送り続けるだけで相手の勝ちを永久に消せる**。
§8 の限界6 として記録した。対応方針は未決定。

### 10.4 方式B を棄却する数値

同じラウンドで、B の `serverElapsed` は A より **149ms** 大きかった（366.30 対 216.98）。
一方、実際の反応時間の差は **30ms** しかない（230.6 対 200.5）。

**回線条件が技量差の約 5 倍を支配している。**
方式B（サーバー受信順）を採ると、この 149ms がそのまま勝敗になる。対戦として成立しない。
§3 の棄却理由が数値で裏づけられた。ただし人工遅延による再現なので、実回線でも確認すること。

### 10.5 60Hz での測定（Mac 内蔵ディスプレイを 60Hz 固定、solo・自動タップ30試行）

システム設定でリフレッシュレートを 60Hz に固定して再測定した。

| 項目 | 中央値 | 最小 | 最大 | 幅 | σ |
|---|---|---|---|---|---|
| `performance.now()` 分解能 | **0.100** | — | — | — | — |
| フレーム間隔 | 16.60 | 16.60 | 16.65 | **0.05** | 0.01 |
| `t_recv → t_paint` | 4.55 | −0.70 | 13.80 | **14.50** | 4.20 |
| `R`（目標200ms） | 200.60 | 199.80 | 201.40 | 1.60 | 0.43 |
| `residual` | **21.48** | 16.00 | **31.03** | 15.03 | 4.21 |

分解能 0.100ms は Chrome の意図的な粗化（§2.1 の「0.1ms〜1ms 程度」の下端）。
60Hz 固定時のフレーム間隔は σ 0.01ms と極めて安定していた。

**`R` の幅 1.6ms は計測精度ではない。** 自動タップは `t_display` の推定値を基準に発火するので、
`R` は構造上ほぼ目標値になる（自己参照）。**自動タップでは表示時刻の推定誤差を測れない。**
実際の計測系のばらつきは `t_recv → t_paint` の幅 **14.5ms** に現れている。
これは「GO がフレームのどのタイミングで届くか」が一様に散るためで、1フレーム（16.6ms）とほぼ一致する。

#### 発見: `residual` の基準値はリフレッシュレートに比例する

| 条件 | `residual` |
|---|---|
| 120Hz（§10.2） | 8〜15 ms |
| 60Hz（今回） | **16〜31 ms** |

`residual` には構造上 `t_recv→t_paint` とフレーム間隔が乗るため、**60Hz の端末は 120Hz の端末より
基準値が 8〜10ms 高くなる**。つまり整合性検査の誤検知リスクは**リフレッシュレートに依存する**。

これは §8 限界1 をさらに悪くする。正直なプレイの `residual` が既に最大 31ms（しかも localhost で、
実回線のジッタは乗っていない）ある以上、`ε` はそれを十分上回る必要があり、
**`ε` を下げて検出力を上げる余地はほとんどない**。

#### `D`（同着幅）の根拠

計測系が `R` に持ち込む誤差は、主に `t_display` の推定誤差。
推定は「1フレーム後」で固定しているので、誤差は概ね ±半フレーム = 60Hz で **±8ms** 程度。
60Hz と 120Hz が混在すれば、さらに系統差が 8ms 程度乗る。

**`D = 20ms` を維持する。** 推定誤差のおよそ2倍にあたり、根拠として妥当。
これ以上広げると引き分けが増えて対戦がつまらなくなるため、カジュアル対戦としてはここで打ち切る。
仮置きの値がそのまま残った形だが、今回は推測ではなく測定値に基づいて決めた。
