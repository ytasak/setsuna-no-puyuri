# SET2-3 マッチメイキング：匿名ユーザーを1対1に割り当てる

> ステータス: **設計確定**
> 対応チケット: [SET2-3](https://linear.app/setsuna-no-puyuri/issue/SET2-3)
> 前提: [SET2-7](./set2-7-embed.md)（kusa は識別情報を渡さない）、[SET2-6 §3](./set2-6-stats-ranking.md)（Cookie identity）、[SET2-2](./set2-2-realtime-match.md)

## 1. 扱う範囲

「人が来てから、2人のルームができるまで」。ルームができた後は SET2-2。

- 単一の待機列
- 参加・キャンセル・待機期限・割り当て・準備完了期限
- 自己対戦と二重所属の防止
- 奇数人数、キャンセルと割り当ての競合、待機中の切断

---

## 2. 3つの識別子を区別する

混同すると自己対戦の防止が効かなくなるので、最初に分けておく。

| 識別子 | 範囲 | 用途 |
|---|---|---|
| `connectionId` | WebSocket 接続1本 | 送受信の宛先。切断で消える |
| `token`（Cookie） | **ブラウザ**（約30日） | **同一人物の判定はここ**。SET2-6 §3 |
| `matchId` | 1ルーム | 対戦の単位 |

**複数タブを開くと `connectionId` は増えるが `token` は同じ。**
接続単位でしか見ていないと、同じ人が自分と対戦できてしまう。

---

## 3. 待機列

### 3.1 MVP は単一列

腕前によるマッチングは行わない。来た順に2人ずつ組む。

- 人が少ないうちは分けても待ち時間が伸びるだけ
- 連勝ランキング（SET2-6 §6.2）はあるが、それをマッチングには使わない

### 3.2 割り当ての規則

待機列の先頭から順に見て、**`token` が異なる最初の2人**を組む。

```
列: [A(token1), B(token1), C(token2)]
     ↑ A と B は同一ブラウザなので組まない
     → A と C を組む。B は列に残る
```

これで**複数タブでの自己対戦を防ぐ**。接続単位の判定では防げない。

### 3.3 二重所属を防ぐ

**1つの `token` が同時に所属できるのは、1つの待機列または1つの対戦だけ。**

同じ `token` で2つ目のタブが参加しようとしたら拒否する。

> 別のタブで参加しています

`connectionId` 単位で許すと、同じ人が2枠を占めて待機列を荒らせる。
また戦績（SET2-6）がどちらの結果か決まらなくなる。

---

## 4. 期限と取りこぼしの解消

完了条件「奇数人数、キャンセル競合、接続断で取り残された待機が解消される」への対応。

| 状況 | 扱い |
|---|---|
| **奇数人数** | 余った1人は列の先頭で待ち続ける。次に来た人と組む |
| **待機期限**（案: 90秒） | 超えたら列から外して「相手が見つかりませんでした／もう一度さがす」を出す。**黙って待たせ続けない** |
| **待機中の切断** | 接続が切れた時点で列から外す。`token` の所属も解放する |
| **キャンセルと割り当ての競合** | 割り当ては1か所で直列に行い、列から取り出した時点で確定させる。<br>取り出し後に届いたキャンセルは**無視**し、そのままルームへ入れる。ルームに入った後の離脱は SET2-2 のケース7（GO前の切断＝無効試合）で処理される |
| **準備完了期限**（案: 30秒） | `MATCHED` 後に片方が `READY` を送らないままなら、ルームを閉じて**両者を列に戻す**。放置で相手を縛らない |
| **相手不在** | 待機・再試行を表示する。**ボットへの暗黙の置き換えはしない** |

### 4.1 ボットで埋めない

人が少ない時間帯にボットを混ぜたくなるが、しない。

- 匿名なので「相手が本当に人だったか」を後から確認できない
- 連勝ランキング（SET2-6）にボット戦が混ざると、記録の意味が変わる
- 混ぜるなら**ボットだと明示する**必要があり、それは MVP の範囲を超える

#### 道場として明示的に用意した（2026-09-14 / §4.2）

**禁じているのは「暗黙の置き換え」であって、明示するなら矛盾しない。**
MVP は公開済みなので、3つ目の理由も消えた。§4.2 に書いた。

上の2つの理由も、**明示する・記録に入れない**ことで両方とも解ける。

### 4.2 道場（一人用モード、2026-09-14 追加）

**人がいない時間でも遊べるようにする。** 待機列に誰もいなければ、ここまでは
90秒待って「見つかりませんでした」で終わりだった。

タイトルに「道場」を置く。段位を上げていく一人用の稽古場。

| 段 | 相手 | 反応時間 |
|---|---|---|
| 一 | 藁の案山子 | 約 360ms |
| 二 | 丸太の門番 | 約 305ms |
| 三 | 白木の門下生 | 約 258ms |
| 四 | 黒鉄の師範代 | 約 218ms |
| 五 | 影の師範 | 約 186ms |
| 六 | 無名の名人 | 約 162ms |

毎回ばらつかせる（σ は段ごとに 55→20ms）。同じ段でも勝ったり負けたりする。
勝てば次の段、負けても引き分けでも同じ相手。段位は下がらない。

**名前は「◯◯のぷゆ△」（人間）と別系統にしてある。** 人と見間違えさせない。
相手の反応時間は `R_min + 12ms` より下に行かないよう止める。
止めないと相手が「速すぎ」でフライング負けになり、稽古にならない。

#### サーバーに何も送らない

道場はクライアントだけで完結する。`ARMED` / `GO` / `RESULT` と**同じ形の
メッセージを自分で作って `onMessage` に流す**ので、計測・演出・音・抜刀・転倒は
対人戦とまったく同じ経路を通る。`send()` を道場へ振り替えているだけで、
`handleInput` から下は1行も分岐していない。

**記録に入らないことが構造で保証される。** サーバーに送らないので、
入りようがない。実際に3戦して WebSocket の送信が空、`/api/summary` が
前後で完全に同一であることを確認した。

#### 判定は本物と同じものを使う

`core/match.js` の `decide()` をブラウザから import する（`public/rules-bridge.js`）。
そのためだけに `/core/match.js` を配信している。

**ここで判定を書き直すと、対人戦と道場で勝敗の基準がずれて稽古の意味が無くなる。**
同着幅も生理的下限も、対人戦とまったく同じ値が効く。

#### 段位の保存

`localStorage`。iframe の中では使えないことがあるので、読めなくても書けなくても
動くようにしてある（その場合はセッション中だけ保持）。
段位は競技記録ではないので、日次リセットの対象にしていない。

### 5.2 1試合で部屋を解散する（2026-09-14 修正 / 不具合）

**公開後、実際に遊んで見つかった。1試合終わったあと「もう一度」を押すと必ず失敗していた。**
画面は「相手を探しています」に変わるが、そこから永久に戻ってこない。

原因は core と待機列の食い違い。

`core/match.js` は決着のあとも部屋を残す。RESOLVED のまま `rematchTimeout`（60秒）だけ待ち、
同じ相手ともう1ラウンドできるようにしてある。これは lab の duel モード（固定の2人で
何度も計測する）の作りで、待機列から来た人には合っていなかった。

部屋が残っていると:

1. `client.room` が立ったままなので `joinQueue` が `if (client.room) return` で**黙って**落ちる
2. token が `engagedTokens` に握られたままなので、仮に 1 を抜けても二重所属として弾かれる
3. 列に入っていないので `waitTimer` も仕掛からない。**`WAIT_TIMEOUT` すら出ない**

3 が効いて、クライアントは「相手を探しています」のまま何も受け取らない。
リロードするまで戻れなかった。

§5.1 に「1試合ごとに列へ戻る」と書いてあったのに、実装がそうなっていなかった。

**直し方**: 待機列から組んだ部屋（`room.queued`）は、結果を配り終えた時点で解散する。
lab の duel モードは従来どおり部屋を残す。

コマンドを配り終えてから消すこと。途中で消すと、同じ配列に残っている
`broadcast` や `setTimer` が死んだ部屋に対して動く。

**出口を2つ用意する。** 「次の相手」だけだと、やめたい人の行き先が無い。
決着と待機期限切れの両方に「タイトルへ」を置く。

### 5.3 引き分けは決着するまで同じ相手と（2026-09-14 追加）

引き分けは**勝負がついていない**。列に戻さず、その場で同じ相手と再戦させる。
元ネタの「いあいぎり」でも、相打ちなら仕切り直して決着をつける。

対象は**引き分け3種すべて**（同着・双方フライング・双方無入力）。
どれも決着していないという点で同じ。

| | |
|---|---|
| 部屋 | 残す。`core/match.js` は RESOLVED のまま `READY` を受け付ける |
| 画面 | **「構える」だけ。** 決着をつけさせたいので、ここに「やめる」は置かない |
| 期限 | 60秒（`rematchTimeout` / 環境変数 `REMATCH_TIMEOUT`）|

決着した試合は §5.2 のとおり解散して列に戻す。

#### 部屋を即座に消すなら、消えた部屋宛ての入力を想定する（2026-09-14 不具合）

「決着したら結果を配った時点で解散する」に変えた直後、**本番が数分おきに落ちた。**

```
TypeError: Cannot read properties of null (reading 'match')
    at handle (adapters/node-ws.js)
        if (room.match) {
```

`handle()` は先頭で `const room = client.room` を取ってから `room.match` を見ていた。
`client.room` が null のときを見ていない。

以前は結果のあと60秒（`rematchTimeout`）は部屋が残っていたので、
遅れて届いた入力にも部屋があり、表に出ていなかった。
即座に消すようにしたことで、**部屋が消えた直後に届いた TAP・READY・LEAVE** が null を踏む。
実回線では毎回起きる。

`room?.match` に直した。消えた部屋宛ての入力は、core が古いイベントを捨てるのと同じく黙って無視する。

**部屋の寿命を縮めるときは、その部屋宛てに飛んでいる最中のメッセージを必ず考える。**

#### 出口は必ず用意する（ボタンを出さないぶんサーバー側で）

「構える」だけにするなら、**押さなかった人が取り残されない**ようにしないといけない。
`#close()` は `closed` をアダプタへ返すだけで、クライアントには何も送っていなかった。
このままだと60秒後にボタンが無反応になり、リロードするまで戻れない。§5.2 とまったく同じ穴。

出口を3つ用意した。

| 状況 | どうなるか |
|---|---|
| 相手が抜けた | 部屋を解散し、残った人を**列に戻す**（決着させる相手がもういない）|
| 誰も構えないまま期限切れ | `ROOM_CLOSED` を送り、**タイトルへ**戻す |
| 自分だけ構えて期限切れ | 同じく `ROOM_CLOSED`。ただし**列に戻す**（やる気がある側なので）|

#### 引き分けの発生率は 18%（実測）

再戦が延々続かないか気になったので、公開初日の実データで測った（`/api/summary`）。

| | |
|---|---|
| 試合数 | 460 |
| 決着 | 375 |
| **引き分け** | **84（18.3%）** |
| 無効試合 | 1.5 |

2連続で引き分ける確率は 0.18² ≈ **3.3%**、3連続は 0.6%。
引き分け1回あたりの追加ラウンドは平均 1.2 回で、**延々続くことはない**。

#### 連鎖の長さを見られるようにした

公開当日に「**4回連続で引き分けた**」という報告があった。18.3% の 4 乗は 0.11% なので、
平均的なペアでは滅多に起きない。起きたということは、**引き分けはペアに偏る**ということ。

引き分けは `|Ra − Rb| ≤ 20ms` なので、**腕前が近い2人ほど差が 0 付近に集まって当たりやすい**。
反応時間のばらつきを σ≈40ms と置いた粗い見積もり（実測ではない）:

| ペア | 引き分け率 | 4連続 |
|---|---|---|
| 拮抗している | 約27% | 約0.5% |
| 50ms 差がある | 約10% | 0.01% |

**再戦方式は同じ相手に留まるので、いちばん引き分けやすいペアから離れない。**
連鎖はむしろ伸びうる。ただし列に戻る手間は消えるので、体感は軽くなるはず。
どちらが効くかは実データで見る。

`/api/summary` の `rounds` が判断材料になる。
何ラウンド目の結果だったかの分布で、`draw` の 4 が多ければ4連続が起きている。

（`decided + draws + voided` が試合数と 0.5 ずれている。
片側の `token` が取れなかった試合が1件ある——切断で `room.clients` から
消えたあとに結果が確定した場合に起きる。460件中1件なので当面は追わない）

### 5.1 連勝は待機列をまたいで続く

1試合ごとに列へ戻るが、**連勝は切れない**（SET2-6 §6.2）。
「勝ったら次の相手」という元ネタの勝ち抜き構造を、単一列で自然に再現できる。

待機中も現在の連勝数を出しておく。次の相手を待つあいだに緊張が持続する。

## 6. 匿名環境の限界

チケットの「匿名環境で別セッションを同一人物と断定できない限界を記録する」への回答。

1. **`token` は「同じブラウザ」であって「同じ人」ではない。**
   Cookie を消す、別ブラウザを使う、プライベートウィンドウを開く、いずれでも別人になる
2. **Cookie を保存しないブラウザでは毎回別人になる**（SET2-6 §3.3）。
   自己対戦の防止もその場合は効かない。**検出はできるが防げない**
3. **したがって自己対戦を完全には防げない。** 同じ人が2つのブラウザで開けば、
   システムから見れば別の2人であり、組んでしまう
4. 同様に、**待機列を1人で複数占めることも完全には防げない**

いずれも日次リセット（SET2-6 §1.1）で実害を抑える方針。
継続的な順位に影響しないので、手間をかける旨味が小さい。
