# SET2-7 iframe組み込み：kusa との起動・通信・セッション境界

> ステータス: **要件は確定。残りは HTTPS での公開のみ**
> 対応チケット: [SET2-7](https://linear.app/setsuna-no-puyuri/issue/SET2-7)

## 1. 確認できた要件（一次情報）

kusa の「開発者向け」ページ（アプリタブ → kusaApp → 開発者向け）に書かれている内容がすべて。
**別途の仕様書も、問い合わせ先も、審査フォームも存在しない。**

> **つくるときのめやす**
> - アプリはこのページの中に iframe で表示されます
> - スマホの縦画面（横幅 360px くらい）で見やすいと嬉しいです
> - 埋め込みを拒否する設定（X-Frame-Options / frame-ancestors）だと真っ白になります
> - https で置いてください
> - 匿名で遊べるものだと kusa になじみます

参加方法は「アプリをつくって URL を運営の Twitter に送る」だけ。

### 1.1 チケット本文の前提との差分

SET2-7 のチケットは、埋め込み元 origin、sandbox/allow 属性、認証情報の受け渡し、
postMessage の仕様、第三者Cookie制限下のセッション確立方式などを確認事項に挙げていた。

**これらはいずれも存在しない。** kusa 側にアプリと情報をやり取りする仕組みが無い。
未取得の仕様を追いかける必要はない。

## 2. 最大の帰結：kusa からユーザー識別情報は渡されない

これが他チケットに効く。

```
kusa のページ
├── ユーザーは kusa にログインしているかもしれない
└── <iframe src="https://…/game.html">
        ↑ ここに渡されるものは何もない。URL パラメータも postMessage も無い
```

つまり **アプリ側は「誰が遊んでいるか」を知る手段を一切持たない。**

| 影響 | 内容 |
|---|---|
| **SET2-6 戦績** | 同一セッション内に閉じるしかない。タブを閉じれば戦績は消える |
| **SET2-6 ランキング** | 「同じ人」を追跡できないので、継続的なランキングは**原理的に成立しない** |
| **SET2-3 マッチメイキング** | 完全な匿名。自己対戦の防止は接続単位でしか行えない |
| **不正対策** | 不正者を継続的に排除できない。別タブを開けば新しい他人になる |

SET2-4 §8 の限界4「匿名環境では不正者を継続的に排除できない」が、
推測ではなく**確定した前提**になった。

ブラウザの `localStorage` に自前の識別子を置けば「同じブラウザ」の継続は追える。
ただしこれは本人証明ではなく、消せるし複製もできる。SET2-6 で扱う。

## 3. 信頼境界

完了条件「kusa とアプリ間の責務・データ・信頼境界を1枚の構成図と通信仕様で説明できる」への回答。

```
┌─────────────────────────────────────────────────────────┐
│ kusa のページ（kusa のドメイン）                          │
│  責務: iframe を置くだけ                                  │
│  こちらへ渡すもの: なし                                   │
│  こちらから渡すもの: なし                                 │
│                                                          │
│  ┌───────────────────────────────────────────────────┐  │
│  │ iframe（**こちらのドメイン**）                       │  │
│  │  ← ここから内側が信頼境界の内側                      │  │
│  │  game.html / game.js                              │  │
│  │  責務: 合図の描画、入力の取得、反応時間の申告          │  │
│  │  **申告値は信用されない**（SET2-4 §5.3）             │  │
│  └───────────────┬───────────────────────────────────┘  │
└──────────────────┼──────────────────────────────────────┘
                   │ WSS（同一オリジン）
                   ↓
        ┌──────────────────────────────┐
        │ 対戦サーバー（こちらのドメイン） │
        │  責務: ルーム管理・判定・記録    │
        │  信用するもの: 自分で測った時刻  │
        │  信用しないもの: クライアント申告 │
        └──────────────────────────────┘
```

**境界は「kusa ↔ アプリ」ではなく「ブラウザ ↔ サーバー」にある。**
kusa は何も渡してこないので、kusa との間に検証すべきデータが存在しない。
守るべき境界は、クライアントが送ってくる `R` と `rtt` をサーバーが信用しない点だけで、
これは SET2-2 / SET2-4 で対処済み。

### 3.1 通信仕様

kusa ↔ アプリ: **なし**（iframe に置かれるだけ）
アプリ内: [SET2-2 §4 のメッセージ仕様](./set2-2-realtime-match.md)

## 5. 「不正origin・改ざん識別情報・期限切れセッション」について

チケットの完了条件にあるが、前提が変わったので実態に即して整理する。

**改ざんされた識別情報**: kusa から識別情報を受け取らないので、改ざんの対象が存在しない。
`clientId` はサーバーが接続ごとに発行し、メッセージ中の自己申告は一切使わない（SET2-2 §7）。

**期限切れセッション**: セッションを受け取らないので該当しない。
接続が切れればその `clientId` は消える。

**不正origin**: `ALLOWED_ORIGINS` 環境変数で WebSocket の Origin を制限できるようにした（既定は無効）。

```bash
ALLOWED_ORIGINS="https://自分のドメイン" npm start
```

ただし**これは強い防御ではない**。Origin ヘッダはブラウザ以外のクライアントから自由に詐称できる。
また iframe 内のページの origin は kusa ではなく**こちらのドメイン**なので、
Origin を見ても「kusa から来たか」は判定できない。

実質的な防御は SET2-2 §7 の次の2点で、こちらは実装・テスト済み。

- 参加者リストはサーバーが作る。クライアントから `matchId` を指定して参加できない
- 送信元 `clientId` が参加者かを毎回確認する

## 6. デプロイ要件

HTTPS 公開が唯一残った作業。満たすべき条件は3つだけ。

1. **HTTPS**（証明書込み）
2. **X-Frame-Options / CSP frame-ancestors を出さない**。出すと kusa 側で真っ白になる
3. **WebSocket（WSS）が通る**

デプロイ先の比較は [SET2-2 §9](./set2-2-realtime-match.md)。要点を再掲する。

| | 向いている点 | 注意 |
|---|---|---|
| Cloudflare Workers + Durable Objects | 無料枠で足りる。`workers.dev` で HTTPS が無料 | **デプロイ後は `Date.now()` が I/O のたびにしか進まない**。`serverElapsed` が整合性検査の土台なので実測必須。ローカルでは再現しないので `wrangler dev` では気づけない |
| Node + ws を常駐ホストに置く | 現行コードがそのまま動く。時計が素直 | ホスト代がかかる。HTTPS の用意が要る |

判定ロジックは `core/match.js` に切り出してあるので、どちらを選んでも作り直しにはならない。
