# reaction-lab

SET2-4「同期・公平性」の実測と、SET2-2「リアルタイム対戦」の検証用プロトタイプ。

判定仕様の本体は [`../../docs/set2-4-sync-fairness.md`](../../docs/set2-4-sync-fairness.md)、
状態遷移とメッセージ仕様は [`../../docs/set2-2-realtime-match.md`](../../docs/set2-2-realtime-match.md)。

## 構成

```
core/match.js        … 状態遷移と判定。I/O を持たない。時計とランダムは外から注入する
core/match.test.mjs  … 偽の時計による単体テスト（31件）
adapters/node-ws.js  … Node + ws アダプタ。人工遅延・CSV 記録・サーバー発 PING
test/e2e.test.mjs    … WebSocket 越しの結合テスト（12件）
server.js            … エントリポイント
public/              … 計測用クライアント
```

core を I/O から切り離してあるのは、Cloudflare Durable Objects など別の土台にも載せられるようにするため
（SET2-2 §9.5）。アダプタを書き換えれば core はそのまま使える。

## テスト

```bash
npm test
```

43件、約12秒。実時間を待たないよう単体テストは偽の時計で駆動し、
結合テストはサーバーを同一プロセスで起動する。

## 起動

```bash
npm install
npm start
```

起動時にローカルURLと**LANのURL**を表示する。スマホからは LAN のURLを開く（同一ネットワークにいること）。

| パス | 用途 |
|---|---|
| `/game.html` | **プレイ用**。刹那のぷゆりの体験プロトタイプ（SET2-5） |
| `/` | 計測用の lab。診断値とCSVを取る（SET2-4） |

```
http://localhost:8787/game.html
```

**同じブラウザで2タブ開いても対戦できない。** 同一 Cookie ＝同一 token なので、
自己対戦の防止（SET2-3 §3.2）が働いて組まれない。2人で試すには Cookie を分ける。

| 方法 | やり方 |
|---|---|
| オリジンを分ける | 片方を `http://localhost:8787/`、もう片方を `http://127.0.0.1:8787/` で開く |
| シークレットウィンドウ | 片方を通常、もう片方をシークレットで開く |

```bash
COOKIE_SECURE=1 npm start   # 本番相当。Secure + SameSite=None + Partitioned が付く
WAIT_LIMIT=90000 READY_LIMIT=30000 npm start
```

閾値は環境変数で振れる（§6 の「実測で決める値」に対応）。

```bash
W_MIN=1000 W_MAX=4000 T=3000 D=20 R_MIN=100 PORT=8787 npm start
```

| 変数 | 意味 | 既定値 |
|---|---|---|
| `W_MIN` / `W_MAX` | ランダム待機の範囲 [ms] | 1000 / 4000 |
| `T` | 入力期限 [ms] | 3000 |
| `D` | 同着幅 [ms] | 20 |
| `R_MIN` | 生理的下限 [ms] | 100 |

## URLパラメータ

```
/?room=lab&mode=duel&name=自分&label=iPhone15-5G&delayUp=0&delayDown=0
```

| パラメータ | 意味 |
|---|---|
| `room` | ルーム名。同じ値を開いた2人が対戦する |
| `mode` | `duel`（2人）または `solo`（1人・計測のみ） |
| `name` | 表示名 |
| `label` | 端末・回線条件のメモ。CSV にそのまま入るので条件ごとに変えること |
| `delayUp` | 端末→サーバーの人工片道遅延 [ms] |
| `delayDown` | サーバー→端末の人工片道遅延 [ms] |

**人工遅延は実回線の代用**であり、実機・実回線での確認を省略してよい理由にはならない。
非対称回線は `delayUp` と `delayDown` に異なる値を入れて再現する。

## 測定手順

### §7.1 計測系のばらつき（同着幅 `D` の下限を出す）

1. `mode=solo` で開く
2. 「キャリブレーション実行」を押す → `performance.now()` の分解能を測り `data/calib-*.csv` に記録
3. 「自動タップ」を ON（目標 200ms）にして 30 ラウンド以上回す
4. `data/rounds-*.csv` の `recvToPaint_ms`・`frameInterval_ms`・`R_ms` の分散を見る

> 自動タップは `setTimeout` のジッタを含むため、`R_ms` の分散＝計測系の分散ではない。
> 分解能・フレーム間隔・`recvToPaint_ms` の各分布を主な根拠にし、`R_ms` は参考値として扱う。

### §7.2 端末差

手持ちの端末それぞれで `mode=solo` + キャリブレーションを実行し、`label` を端末名にする。
`refreshHz_est` が 60 / 120 で割れることを確認する。この差が系統的な有利不利になる（§7.2 の記載どおり）。

### §7.3 通信条件

| 条件 | 方法 |
|---|---|
| 同一LAN | そのまま |
| モバイル回線 | スマホをテザリング解除して 4G/5G から接続（サーバーを外部公開する必要あり） |
| 人工遅延 | `?delayDown=80&delayUp=80` などを付けて接続 |
| 非対称 | `?delayDown=120&delayUp=20` |
| ブラウザ側スロットリング | Chrome DevTools → Network → Throttling |

各条件で `rttMedian_ms` / `rttP95_ms` / `rttJitter_ms` を記録する。
**方式B（サーバー受信順）を棄却する根拠**は、`serverElapsed_ms` の差が `R_ms` の差より大きくなることを示せば足りる。

### §7.4 異常系

| 試すこと | 操作 | 期待 |
|---|---|---|
| フライング | 緑になる前にタップ | 押した側の負け |
| 双方フライング | 2人とも先押し | 引き分け |
| 連打 | 合図後に連打 | 最初の1回のみ採用、`extraTaps` に回数が入る |
| 無入力 | 何もしない | 期限超過で判定 |
| GO後の切断 | タブを閉じる / 機内モード | 残った側の不戦勝 |
| バックグラウンド化 | 合図待ちで別アプリへ | サーバー推定値に差し替え、戦績に記録されない |
| 偽造申告 | 「申告値を偽造」を ON | サーバー推定値に差し替えられ偽造側が負ける。戦績には記録されない |

### §7.5 記録

結果は `data/rounds-*.csv`（ラウンドごと・プレイヤーごとに1行）と `data/calib-*.csv` に自動で追記される。
クライアント側の「ローカルCSV」ボタンでも自分の分だけ落とせる。

意味のある測定回の CSV はコミットして残す。試し打ちのものは消す。

## 判定の優先順位

`server.js` の `decide()` は §5 の表を次の順で評価する。

```
切断(GO前) > フライング・速すぎる入力 > 切断(GO後) > 無入力 > 同着 > 反応時間比較
```

複数の条件に当てはまる場合は上位が勝つ。

`R < R_MIN` は「反応」ではなく予測入力なので、フライングと同じ層で扱い、押した側の負けにする。

## 不正対策について

**弾くのは `R < R_MIN`（100ms）だけ。** 整合性検査は 2026-09-13 に廃止した
（設計文書 [SET2-4 §5.3](../../docs/set2-4-sync-fairness.md)）。

理由は、検査が**難しいほうの不正しか防げていなかった**から。

| | 内容 | 検査は |
|---|---|---|
| A | 人が普通に遊び、数字だけ書き換えて申告する | 捕まえられた |
| B | スクリプトが合図を検知して押す（自動化） | **捕まえられない** |

B が捕まらないのは、自動化したクライアントは申告と実際の送信タイミングが一致しているから。
そして **B のほうが作るのは簡単**。一方で、正直な 60Hz ユーザーを誤検知するリスクだけは残っていた。

`R_MIN` は残している。素朴なボットは合図の直後に押すので `R` が数 ms になり、
ここで弾かれて負ける。**ボットはわざと 100ms 以上まで遅らせる必要がある。**
人間の下限が概ね 150ms 前後とされるので 101ms のボットは常に勝つが、それ以上速くはなれない。

`residual = serverElapsed − R − RTT中央値` は引き続き算出して CSV に残しているが、
**判定には使わない**。計測が健全かを見るための診断値。
